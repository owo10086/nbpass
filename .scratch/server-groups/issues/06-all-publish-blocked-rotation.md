# 06: 全部发布组成员被墙：摘除、换 IP、按加回规则恢复

**What to build:** 全部发布组不选被墙处理策略，固定为：成员被墙先摘除（受最少保留数约束）；节点开了换 IP 就换（换 IP 申请用途新增"全部发布组成员"）。新地址确认后，所有绑定该节点的记录（各全部发布组成员记录、入口节点记录、主备组按现有规则）改为新地址，全部发布成员记录保持当时的启用或暂停状态；新 IP 复检通过并满足票 05 的加回条件后才启用。因最少保留数未被摘除的成员，记录也随新地址确认改为新地址，保持启用。跨组换 IP（票 32）的切离屏障扩展到全部发布组：换 IP 前该节点在所有全部发布组中先完成摘除或被判保留，再统一换一次。

**Blocked by:** 05

**Status:** ready-for-agent

**Refs:** 规格用户故事 8；GLOSSARY「被墙处理策略」；票 31、32；`cross_group_rotation.go`、`rotation.go`、`exit_blocked.go`

- [ ] 成员被墙 → 摘除 → 换 IP → 新地址确认后记录改为新地址且仍暂停 → 复检通过并连续检查成功 → 启用；假 DNSPod 记录值与状态依次正确
- [ ] 节点关闭换 IP 时只摘除并通知
- [ ] 换 IP 失败、受限、待确认或冻结时保持摘除并通知
- [ ] 单成员组：成员被墙时保留不摘除，照常换 IP，新地址确认后记录改为新地址且保持启用；复检失败时继续保留并通知
- [ ] 节点同属主备组和两个全部发布组时，换 IP 只执行一次；主备组完成切离、两个全部发布组完成摘除或保留后再换；换完各组按自己的规则恢复
- [ ] 以上行为由测试台通过面板 HTTP API、假换 IP 接口与假 DNSPod 验证
