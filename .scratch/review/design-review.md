## 一、确定的问题

### C01｜入口切换、换 IP、DNS 写回缺少统一的动作协调【高；A】

**问题与依据：**决定 8、10、11、16 都会影响入口地址或 DNS，没有定义谁拥有最终期望值、并发顺序和崩溃恢复方式。

**失败场景：**A 切到 B 时，解析监控按旧“活动入口=A”写回；随后 A 换 IP 的完成消息又把域名改回 A，绕过新 IP 验证。即使每条 API 调用成功，流量仍可能来回跳转。

**建议：**由面板统一维护入口组的期望版本、期望成员和进行中动作；DNS 监控只提交偏差事件，交给同一执行器写回。按入口组协调 DNS、按节点协调换 IP；每次外部调用及迟到结果都核对动作 ID 和版本。将“期望已变更、服务商已写入、解析待传播、业务验证完成”分开持久化，重启后先核对再续做。手动操作也走同一路径。

### C02｜换 IP 请求具有“可能已执行但结果未知”的状态【高；A、B】

**问题与依据：**决定 11 正确地要求观察 IP 变化，但尚未覆盖 HTTP 超时、任务重发及执行中断线。推送与全量同步也不能自动保证外部动作只执行一次。

**失败场景：**商家已经换 IP，响应丢失，节点重启后再次调用；或命令收到后搁置，节点失联时才执行，违反“不离线自行换 IP”。按 HTTP 失败立即重试可能连续释放可用地址。

**建议：**配置快照与一次性命令分离；调用前持久化动作 ID、旧地址和额度占用。使用有限有效期的执行许可，执行前确认控制连接及授权仍有效；调用后失联则只继续观察和记录。超时进入“结果未确认”，优先核对地址，不能假定失败重发；供应商不支持幂等时，不承诺严格的恰好执行一次。

### C03｜“节点公网 IP”不能同时代表所有业务地址【高；B】

**问题与依据：**决定 11 以节点上报的公网 IP 变化判成功，但未区分出站源地址、入口发布地址、隧道连接地址和检测地址。

**失败场景：**NAT 节点的出站 IP 变了，入站映射没有变；多 IP 节点只换了默认出站地址；面板据此更新 A 记录，却指向不能接收入站流量的地址。

**建议：**节点 ID 独立于 IP；明确维护出站观测地址与各角色的可连接端点。换 IP 任务绑定具体 IPv4 端点及旧值，过滤无效地址，并用入站验证确认其用途。v1 若只支持“一节点一个直接可入站公网 IPv4”，应明确校验和拒绝不支持的 NAT、多 IP 自动恢复场景，不能默默当作支持。

### C04｜出口换 IP 后存在地址更新与隧道重建窗口【高；B】

**问题与依据：**决定 2、5、11 要求节点失联继续转发、校验证书、出口换 IP 后更新入口配置，三者无法保证无缝完成。

**失败场景：**出口已释放旧 IP，部分入口尚未收到新地址，仍拨旧地址；控制链路此时中断，这些入口只持有旧缓存。证书如果绑定旧 IP，新地址即使已下发也握手失败。

**建议：**记录端点版本，分开展示“IP 已变化、哪些入口已应用、哪些入口已成功握手”。尽量使用不随 IP 变化的出口身份名称；地址更新后重建新会话。允许供应商保留旧地址时再安排排空，否则明确已有 TCP 连接可能断开，缓存不能消除该中断窗口。

### C05｜全量同步尚缺少版本、应用确认和重连对齐契约【高；A、B】

**问题与依据：**决定 2、4 与 ADR 0001 定义了通信方式，但“收到配置”和“配置实际生效”不是同一状态。

**失败场景：**旧流迟到的配置覆盖新配置；某入口监听失败却被标“正常”；节点离线时切过目标，重连后用旧报告覆盖面板期望；离线期间删除的规则重连后被恢复。

**建议：**配置携带单调版本和摘要，节点校验、原子持久化、应用后报告实际版本与逐规则错误；区分期望状态、运行状态和观测状态。旧流、旧版本及旧进程报告不得覆盖新状态；删除需要能通过完整快照或删除标记收敛。入口组同步状态须表达成员部分成功及离线过期状态，不能只给一个无说明的“正常”。

### C06｜HTTP 后端与公网安全链路的边界没有写完整【高；B、C】

**问题与依据：**决定 1 将 HTTPS 交给反向代理，决定 2 使用 token；ADR 0001 没有规定节点到代理的 TLS 验证。仅 HTTP 后端本身并非错误，缺口在两条对外链路的部署契约。

**失败场景：**网页经 HTTPS，独立 gRPC 端口却直接暴露 h2c，token 与配置可被窃听；代理不支持正确的 HTTP/2 上游或长流，导致周期性假离线。面板或其代理若依赖自身管理的转发入口，入口出问题还可能同时切断恢复控制链路。

**建议：**公网网页和节点控制都经验证身份的 TLS；明文后端限环回或明确可信网络，禁止证书失败自动降级。给出两端口代理示例、节点首次信任、长流超时与保活规则。控制端点应独立于被管理的业务链路，并说明面板在国内、国外时节点能否稳定连接；面板所在位置不能替代国内检测点。

### C07｜密码哈希与限流尚不能覆盖登录会话安全【高；C】

**问题与依据：**决定 1 已确定仅密码、无 2FA，但没有定义会话期限、撤销和反向代理信任。

**失败场景：**会话永久有效，改密码后旧会话仍能改 DNS；伪造转发头绕过 IP 限流，或所有请求被当成代理同一 IP 导致管理员被锁；带 Cookie 的跨站请求触发升级。

**建议：**使用成熟的加盐密码哈希及校验并发上限；定义可撤销会话、空闲和绝对期限，改密码后撤销旧会话。Cookie 设置 HttpOnly、Secure、SameSite，并对写请求做同源/CSRF 防护；仅信任配置中的代理。提供本机密码恢复方式。这些措施不要求改变无 2FA 的决定。

### C08｜不同凭据的作用域、保存与撤销尚未分清【高；C】

**问题与依据：**决定 2、5、11、14、15 涉及节点 token、入口—出口令牌、换 IP 凭据、DNS 凭据、Telegram 凭据和安装命令。

**失败场景：**把长期节点 token 放进安装 URL、访问日志或 Shell 历史；一个节点拿到其他节点的换 IP 凭据；删除 token 后已建立 gRPC 流仍可上报和接收秘密；被盗节点凭据能够冒充其他节点的检测结果。

**建议：**各类凭据独立，绑定节点或节点对，节点只能上报自身身份及获派任务。安装命令优先携带短期一次性票据，兑换长期 token；避免秘密进入 URL 和日志。DNS、Telegram 凭据留在面板；换 IP 凭据只给执行节点，尽量限定单实例权限。文件权限、备份脱敏/加密、密钥保存和轮换一并规定；撤销须影响已有控制流。可验证的随机 token 仅存哈希，必须再次下发的秘密则需要受保护的可恢复存储。

### C09｜自定义换 IP HTTP 接口需要明确受信任调用边界【高；C】

**问题与依据：**决定 11 允许 URL、方法、头、体和模板，属于高权限网络调用能力。

**失败场景：**接口重定向把 Authorization 带到其他主机；模板变量破坏 JSON/URL 结构；节点可被诱导访问云元数据接口；响应内容和请求头进入事件日志或 Telegram，泄露凭据。

**建议：**仅管理员能配置，节点不能自行改请求模板；按 URL、JSON、请求头上下文正确编码，不拼 Shell。明确允许的目标，校验重定向、超时、响应大小和代理使用，日志脱敏。内网换 IP 服务可能是合法需求，宜显式授权具体端点，不能一律禁内网，也不能默认任意内网均可访问。公网携带凭据的接口使用 HTTPS。

### C10｜自签信任与 Noise 库仍需具体身份和轮换协议【高；B、C】

**问题与依据：**决定 5 的安全方向正确，但“只信任该证书”和“使用 Noise 等成熟库”还不足以唯一确定可互通、安全的协议。

**失败场景：**入口保留系统根，从而接受并非该出口的证书；证书名称绑定旧 IP；更新出口证书时入口尚未取得新信任材料；WS 内先发送令牌、后开始加密，造成令牌明文暴露。

**建议：**明确每出口专用信任集合、稳定身份名称/SAN、有效期和校验方式，不以跳过校验解决地址变更。轮换采用新旧材料短期重叠，并等待应用确认。WS 加密须固定成熟握手模式、对端身份绑定、PSK 作用域、版本和防重放要求；认证及加密完成后再传令牌、建立 yamux 业务流。

### C11｜“只放行规则目标”需要落实到每个逻辑流【高；C】

**问题与依据：**决定 5 已要求目标授权，仍缺少域名目标和配置不同时生效时的验证契约。

**失败场景：**已认证入口在同一 yamux 会话中提交其他规则或任意 IP；只核对目标域名字符串，却拨打入口自行指定的地址；入口先收到新规则，出口尚未收到授权，导致全部新连接被拒绝。

**建议：**每个流核对入口身份、规则归属、授权目标和配置版本，出口依据自己的授权配置决定可拨端点。说明域名由谁解析、IPv4 多地址如何处理，以及合法私网目标的授权方式。新增先准备出口授权，再启用入口；撤销按明确顺序处理。不能把“知道节点对令牌”视为任意转发权限。

### C12｜现有被墙证据不能唯一定位封锁，且会漏掉部分封锁【高；B、F】

**问题与依据：**决定 9 已明确采用自测触发、所有有效点失败确认、无点直接认定。其局限是确定存在的，不是尚未确认的产品选项。

**失败场景：**防火墙误关检测端口时所有点失败，系统换 IP 也无改善；某运营商封锁入站，但节点访问国内网站正常，根本不进入确认；三个检测点失败、一个成功，按规则仍“不算被墙”；无检测点时本机出站路由或多个目标站点故障会直接触发被墙处理。

**建议：**保留已确认判定规则，但记录“多点确认/无检测点推定”的证据等级，并显示覆盖范围，不能宣称全国不可达或确定由 GFW 导致。检测端口应确认监听、地址及防火墙条件；DNS 失败、执行错误与 TCP 不可达分开。若未来要覆盖局部或仅入站封锁，需要另行确认新的触发/判定策略，不能偷偷改变“任一成功即不算”的决定。

### C13｜国内检测点的有效性必须绑定同轮证据和被测地址【高；A、B】

**问题与依据：**决定 9 的国内对照站点校验只能证明部分出站网络正常；ip2region 是归属信息，也不是实际探测路径证明。

**失败场景：**仅能连接国内站点的检测点仍无法访问任何境外网络；检查集合在一轮中途缩小到零，结果反而变成“直接确认”；换 IP 后迟到的旧地址失败样本触发再次换 IP；节点把自己列为检测点，NAT 回环结果左右自身判定。

**建议：**每轮固定检测点集合、目标 IP/端口和配置版本，规定结果期限、缺报和执行错误语义。对照成功与目标探测应在同一有效时间窗；排除自身确认，保留原始结果及覆盖信息。换 IP 后重新识别地区并核对角色，支持用户覆盖；没有新鲜样本不能沿用旧“健康”。集合失效后如何使用已确定的无点降级，应显式记录原因，不能把超时默认为真实连接失败。

### C14｜备用入口“节点在线”不足以证明可接流量【高；B】

**问题与依据：**决定 4 要求同端口同规则，决定 8、10 要选可用备用，但未定义备用就绪条件。

**失败场景：**备用控制流在线、检测端口可达，实际业务监听被占用，或隧道凭据/出口授权未同步；DNS 切过去后新连接全部失败。

**建议：**切换前核对入口组当前规则版本、监听应用结果、所需出口握手及新鲜的国内可达结果。为“备用就绪”单列状态，并说明某条规则未就绪时是否允许承接整组。该检查用于选择候选，不能擅自增加决定 8 之外的入口切换触发条件。

### C15｜DNS API 成功和连续三次旧解析不能直接代表切换结果【高；A、B】

**问题与依据：**决定 16 在切换后每 30 秒检查、连续三次异常；尚未结合旧 TTL、负缓存和传播期限。

**失败场景：**旧 TTL 为 600 秒，正常缓存 90 秒后就被报为异常；另一个检测点先看到新值，系统宣布“已生效”，仍使用旧缓存的用户却无法连接。若据短暂恢复立即回切，两个方向的缓存会重叠。

**建议：**分别保存期望值、服务商记录、各路径解析值；传播期展示旧/新集合及每路径状态，观察期限至少考虑旧 TTL、负缓存及供应商行为。定义何为“生效”、何时结束 30 秒加速及最大观察时长。连续三次阈值按同一路径和同一期望版本计算；传播中的旧值不应被称为污染，解析异常继续仅通知。面板 DoH 是一条加密查询路径，不保证处于境外或答案绝对正确；无国内检测点时标记国内覆盖缺失，DoH 不通记采样失败。

### C16｜DNS 自动写回需要唯一记录归属和供应商模式约束【高；A、B、C】

**问题与依据：**决定 3、8、16 只管理入口 A 记录，但尚未规定记录 ID、线路、代理模式和其他已有记录的处理。

**失败场景：**两个入口组绑定同一域名，互相写回；Cloudflare 开启代理后公共 DNS 返回代理地址，被持续报为不符；DNSPod 多线路记录被覆盖；残留 AAAA 使部分客户端走不受支持的 IPv6。

**建议：**唯一绑定供应商账号、区域/域名、记录 ID、类型和线路。v1 建议明确支持 DNS-only A、单一受管线路；不支持的代理、CNAME 或多线路配置应提示并拒绝自动管理。发现非受管 A/AAAA 需报告影响，不能自动删除他人的记录。递归 DNS 差异不得直接驱动服务商写回。

### C17｜后备出口组缺少环路与全故障保护【高；A、B】

**问题与依据：**决定 6、G“后备出口组”允许组引用，没有约束引用图。

**失败场景：**A 后备为 B、B 后备为 A；全部故障后递归选择不结束。同一出口出现在多个候选组时被重复拨号，累计超时显著增加。

**建议：**禁止自引用和环，v1 可只允许一层后备关系；每个新连接对实际出口去重，设置总尝试预算。全部不可用时明确返回失败，不得自动绕过必经出口改为直连。主组恢复后的重新选择见 Q05、Q07。

### C18｜业务拨号失败必须限定故障归属和重试阶段【高；A、B】

**问题与依据：**决定 7 已确认业务拨号失败立即判故障，但没有定义故障作用域和错误分类。

**失败场景：**出口已正常认证，只是该出口连某目标失败，却被标为整个出口故障，其他规则也被切走；入口本机文件描述符耗尽导致所有目标被摘除；已向目标发送数据后改连另一个目标并重放，产生重复业务操作。

**建议：**保留“立即判故障”，但分别归属入口—出口路径、出口—目标路径、目标或本地资源错误；配置/授权错误单列。仅在尚未建立业务上游、未交付业务数据的阶段按预算换候选；建立后的失败终止该连接，不重放应用字节，也不迁移已有连接。

### C19｜探测频率和阈值尚不能保证恢复时间【中；B、F】

**问题与依据：**决定 7、9 的“约 15 秒”和每两分钟一轮还受拨号超时、调度及候选规模影响。

**失败场景：**多个超时目标串行检查，一轮超过 5 秒；所有节点整点探测导致峰值；某次检测未执行，却被累计成失败。故障判定、候选重试、DNS 缓存相加后，用户恢复远慢于界面显示的 15 秒。

**建议：**规定单次、单轮和新连接总期限，使用有限并发、抖动及按实际路径去重的检查。区分失败与未完成；连续成功 60 秒要求新鲜样本覆盖该窗口，不能只等墙上时间。展示实际采样时间，并把探测判故障时间与业务恢复时间分开。

### C20｜节点角色、组成员关系和端口占用需要统一约束【高；B、D】

**问题与依据：**决定 4 要求组成员同端口监听，但未限制同一节点加入多个入口组、兼任出口以及随机端口的分配方式。

**失败场景：**两个入口组在同一节点占用相同监听端口；随机端口按成员各生成一次，导致组内不一致；隧道、检测和规则监听互相冲突；批量导入部分成功后界面误以为整批已生效。

**建议：**为节点的监听地址、协议、端口建立统一冲突校验；随机端口按逻辑规则选一次并检查所有成员，节点实际 bind 结果仍须确认。说明角色可否重叠，并拒绝明显的自连循环。JSON 使用版本化格式和稳定对象引用，先整体预检，明确新增/覆盖语义；数据库保存成功与各节点应用成功分开展示，默认不导出秘密。

### C21｜SHA256 不能替代升级包来源认证，更新器还涉及提权边界【高；C、F】

**问题与依据：**决定 15 已要求摘要校验和独立 systemd 更新服务，但未规定摘要信任源及更新器可接受的输入。

**失败场景：**二进制与摘要一同经未认证 HTTP 被替换，校验仍通过；普通节点进程向 root 更新器提交任意下载 URL、目标路径或 Shell 参数，形成任意代码执行。

**建议：**经已验证 TLS 获取绑定任务、版本、平台、大小和摘要的清单；若要求独立于分发面板验证发布身份，再使用固定发布公钥验签，不把签名说成现有决定。更新器只接受固定产物与安装路径，不执行节点给出的任意命令，防路径及符号链接替换；下载、校验、自检完成后再停服。

### C22｜升级成功、回滚与维护期间的自动化缺少联动【高；A、B、F】

**问题与依据：**决定 15 的“新版回连且版本一致才成功”是必要条件，但不足以证明转发正常；升级还会触发决定 8、14 的离线逻辑。

**失败场景：**新版能回连却监听失败，升级被宣布成功；升级超过离线阈值，系统改 DNS 或同时发起恢复动作；仅因面板暂时不可达就不断回滚；串行升级遇到未确认后继续处理备用，最终两台都不可用。

**建议：**动作绑定升级任务 ID、进程实例和实际产物，除回连版本外还核对本地运行就绪状态；区分启动失败、业务自检失败和仅控制确认失败。引入有期限的维护状态，协调换 IP、入口切换和通知；业务与安全探测仍记录。批量默认在失败/未确认时暂停，明确升级会断开该进程承载的连接，不承诺无损。

### C23｜同版本要求不能替代滚动升级所需的协议兼容【高；B、F】

**问题与依据：**决定 15 要面板先升级、节点逐台升级，这必然产生新旧版本共存期。

**失败场景：**新面板拒绝旧节点连接，旧节点无法接收升级命令；入口先升级后不能与旧出口握手；新版修改节点缓存格式，回滚旧二进制后无法启动。

**建议：**分开软件版本、控制协议、隧道协议和能力集；至少定义本次滚动升级及回滚覆盖的兼容窗口，保留基础升级通道。节点状态格式也须兼容或可恢复；逐台升级时固定目标版本和产物，避免面板再次升级改变正在执行的批次。

### C24｜SQLite 备份、保留期与自动化安全状态之间有约束【高；B、F】

**问题与依据：**决定 14 允许自定义保留期，决定 15 自动备份 SQLite，但未区分可清理历史与必须保留的当前安全状态。

**失败场景：**直接复制 WAL 模式的主库文件漏数据；清理换 IP 历史后小时/日配额失效；恢复旧数据库把 DNS 期望值及凭据退回过去，监控随即写回旧入口；磁盘满时动作已执行但记录未落盘。

**建议：**采用一致性备份并覆盖密钥、必要设置及恢复说明；明确数据库迁移失败的恢复范围。冷却/配额、未完成动作、配置版本和累计计数独立于可删历史，保留期不得破坏其最小安全窗口。恢复后先核对节点与服务商外部状态，再恢复自动写操作。控制事件和分钟指标分批写入，清理不长时间阻塞控制；关键动作意图无法持久化时不启动外部动作。

### C25｜流量、连接数与分钟曲线缺少统一统计口径【中；B、D、F】

**问题与依据：**决定 13 要规则累计流量、当前连接数及节点分钟曲线，离线缓存和 yamux 会造成不同统计层次。

**失败场景：**入口、出口各报一次而流量翻倍；全量重传重复累计；进程重启计数归零形成负增量；把两条 yamux 物理连接当成只有两个业务连接；离线空白画成零负载。

**建议：**规则业务流量选定单一计量端，说明上下行及隧道开销；累计数用节点/进程标识和序号去重，重启与规则修改保持可追踪。业务连接、隧道载体连接和系统 TCP 数分开。定义分钟聚合、速率采样、运行时长及离线补报界限；缺失数据标缺失，历史清理不能清零规则累计量。

### C26｜itdog 需要隔离故障、输入输出与数据披露【中；C、F】

**问题与依据：**决定 12、ADR 0002 已正确规定手动查看且不驱动自动化，但网页模拟仍是不稳定的外部依赖。

**失败场景：**验证码或页面变更使任务永久占用工作线程；返回文本进入 HTML 展示造成注入；错误响应被画成全省不可达；管理员误把内部目标或带凭据 URL 提交给第三方。

**建议：**独立适配与任务队列，设置并发、总超时和失败状态；只提交明确的地址/端口，展示第三方披露范围。输出作为不可信数据转义，缺点、超时和零成功分别表达，保存任务时间及实际覆盖。保持与自动动作的数据通路隔离；不把页面失败解释为节点故障，也不承诺始终可用。

### C27｜离线事件和通知投递需要与业务动作解耦【中；B、F】

**问题与依据：**决定 2 允许离线本地切换，决定 14 要全部面板事件和 Telegram 通知；离线时无法实时保证中心记录完整。

**失败场景：**节点离线期间多次切出口，回连仅报最终状态，切换历史丢失；重传产生重复通知；国内面板无法连接 Telegram，通知调用阻塞恢复操作或静默丢失。

**建议：**节点为关键事件维护有界持久队列，携带事件 ID、发生时间和关联配置版本，面板去重入库；溢出明确标记缺口。通知异步投递，记录失败、重试和过期，按事故合并；通知失败不能阻塞切换，也不能因反复投递再次执行动作。面板本地记录作为可查看依据，Telegram 的可达性另行展示。

### C28｜Go 用户态转发与复用连接需要资源和故障范围预算【高；B、F】

**问题与依据：**决定 3、5 采用 Go 用户态转发和 yamux，但尚无连接数、内存、缓冲、握手与空闲超时的边界。

**失败场景：**大量半开连接或慢读业务耗尽文件描述符、协程和内存，控制流仍在线却已不能接流量；一个承载大量业务流的 yamux 连接断开，同时影响这些流，不能靠“已有连接不迁移”恢复它们。

**建议：**限定节点/规则并发、待拨号数量、会话流数和缓冲总量，设置握手/拨号期限及可配置空闲策略，正确处理 TCP 半关闭和取消清理。限制握手与探测消耗，避免挤占业务及控制。按实际预期并发和带宽验证 CPU、内存、吞吐与长连接；明确单个复用载体失效的影响范围，不能把引入 yamux 等同于性能已达标。

## 二、需要用户决定的问题

以下不把未定行为写成既定缺陷；每项给出建议默认值，供后续确认。

### Q01｜“失联暂停入口切换”的执行方是什么【高；A】

**问题与依据：**决定 2 写失联时入口切换暂停，决定 8 又要求离线超时并经国内确认后入口切换。两者在执行方相同时冲突，在执行方不同时可以兼容。

**失败场景：**面板因为活动入口控制流断开而禁止改 DNS，决定 8 永远不会触发；反向实现则可能让失联节点自行操作 DNS。

**待决定与建议：**明确为“节点不得自主改 DNS；面板仍存活、证据有效时，可按决定 8 切换失联入口；面板停止时没有入口切换执行者”。还需给出业务离线超时，不能擅自把通知默认 2 分钟等同于故障切换阈值。

### Q02｜无国内检测点时，策略③怎样验证新 IP 并回切【高；A、B】

**问题与依据：**决定 9 已确定无点直接认定被墙；决定 10 的策略③却要求新 IP 经国内检测点验证后切回。现有决定没有给出此时的完成条件。

**失败场景：**先切到备用并成功换 IP，但全部检测点失效，任务永久“等待验证”；若把 IP 变化视为验证成功，就绕过了策略③要求。

**待决定与建议：**无点确认规则继续按已确认决定执行，但策略③留在健康备用并通知“IP 已变化、国内可达性未确认”，待检测点恢复或用户显式处理；不自动降低回切验证要求。仅换 IP 策略也要分开显示地址变化和可达性未确认。

### Q03｜同一节点属于多个入口组时，冲突策略怎样合并【高；A、B】

**问题与依据：**决定 10 按入口组设策略，决定 11 的换 IP 却是节点级动作；是否允许跨组复用尚未规定。

**失败场景：**一组要求“仅切换”，另一组要求“仅换 IP”；后者更换共享节点 IP，影响前者乃至该节点兼任的出口。各组单独计数还可能绕过节点限额。

**待决定与建议：**v1 可禁止入口节点跨组复用以减少组合；若允许，需定义节点级换 IP 授权和冲突仲裁，一次动作关联所有受影响组并共用额度，不由先触发的组隐式决定全局行为。

### Q04｜全部入口不可用或只有一个成员时保留什么【高；B】

**问题与依据：**决定 10 已规定策略③无健康备用时退化为仅换 IP，但策略②以及全部不可用时的 DNS 行为未定义。

**失败场景：**仅入口切换策略没有可选成员，反复在坏节点间切；若删除 A 记录，产生负缓存，使随后恢复更慢。

**待决定与建议：**没有健康候选时保留最后期望解析、停止无意义切换并通知；策略②不隐式升级为换 IP。策略③按已确认退化规则执行，换 IP 受限则保持状态并报告无自动恢复路径。域名此时可能仍指坏入口，界面必须如实标记。

### Q05｜入口回切的优先级、稳定窗口和最短驻留时间是多少【高；A、B】

**问题与依据：**决定 7 已固定目标/出口恢复连续成功 60 秒；决定 8 仅说入口“恢复稳定后自动回切”，决定 10 还有换 IP 后切回，未定义入口优先级和时间条件。

**失败场景：**原入口刚通过一次验证就切回，随后再次异常；多入口连续恢复时争夺“原入口”；DNS 尚未收敛又发生反向切换。

**待决定与建议：**明确固定首选入口及优先级，入口单独设置恢复观察与最短驻留时间，例如先以连续有效成功 5 分钟、驻留至少 10 分钟作为待确认起点，并结合 DNS 传播调整。真实故障可打断驻留保护，旧样本或未知状态不能累计恢复。出口最小连接数策略的“恢复”则是重新加入候选，不是迁移现有连接。

### Q06｜多目标如何选择，隧道目标切换由谁执行【中；B、D】

**问题与依据：**决定 4 和 G 定义“一组目标”，决定 7 给出切换条件，但没有目标优先级/分配策略及隧道中的执行位置。

**失败场景：**入口直测目标失败，出口实际可达却仍切走；多个出口对目标可达性不同，面板维护一个全局“当前目标”产生错误调度。

**待决定与建议：**v1 使用有序主备目标；直连由入口、隧道由实际拨目标的出口维护路径健康和目标选择。若希望入口根据端到端结果选目标，也可行，但须指定唯一决策者及协议，不能两端各自维护互相覆盖的“当前目标”。

### Q07｜最小连接数是每个入口本地统计，还是全局统计【中；B、D】

**问题与依据：**决定 6 没有规定统计范围；决定 2 要求失联时出口选择继续运行，全局精确统计此时无法保证。

**失败场景：**某入口看到出口 A 为零连接，其他入口已把 A 压满；若等待面板全局计数，则失联后无法选择。把 yamux 会话数当业务连接数，几乎无法实现预期均衡。

**待决定与建议：**v1 定为入口本地、按逻辑业务连接及正在拨号的预占数选择，排除探测和物理载体连接；同数时分散选择，并声明不保证全局最优。后备组只在主组全不可用时接管，主组达到已定恢复窗口后供新连接使用。

### Q08｜失联继续转发与安全撤权之间接受怎样的边界【高；B、C】

**问题与依据：**决定 2 已允许按缓存继续转发；面板无法立即把撤销规则或令牌送达失联节点。“已有连接不迁移”也没有说明是否因安全撤销而主动关闭。

**失败场景：**管理员禁用被盗入口的规则，失联出口仍接受缓存令牌；旧 yamux 会话持续开新流，界面却显示已撤权。

**待决定与建议：**明确接受缓存可用性带来的撤权延迟，显示逐节点撤销是否生效，并区分普通切换、规则禁用和安全撤销对已有连接的处理。若要求离线授权自动到期，必须另行确定时长，并承认它会限制当前“继续转发”的可用性；不能同时承诺无限离线运行和即时远程撤权。

### Q09｜换 IP 额度、无改善和暂停解除的精确定义是什么【中；A、B】

**问题与依据：**决定 11 已给 30 分钟、每小时 1 次、每天 3 次、两次无改善暂停，但没有窗口、计数及解除语义。

**失败场景：**按自然小时/自然日计数，在整点或午夜连续两次换 IP；只数成功使超时请求无限重试；无检测点时把“未确认”计为“无改善”，或重启清零绕过暂停。

**待决定与建议：**采用滚动 1 小时/24 小时、请求前计尝试、节点级跨重启保存；这样 1 小时限制通常比 30 分钟冷却更严格，两者不矛盾。“无改善”要求有效的换后验证；未知保持待确认，不当作成功。接口明确失败、IP 未变与换后仍不可达分别记录；暂停由人工解除或符合约定的持续恢复证据解除，手动操作是否允许突破限额须明示。

## 三、术语表的确定偏差与需补充定义

术语表不必复制全部规格；下列事项涉及概念本身，或会直接改变安全和切换语义。

| 位置 | 问题与具体场景 | 程度 | 建议定义 |
|---|---|---|---|
| G“活动入口”（第 31 行） | 以“域名当前解析指向”定义，会在不同递归缓存同时指 A/B 时失去唯一值；决定 16 又以它生成 DNS 期望，形成循环 | 高 | 定义为面板选定、计划发布的唯一成员；另列服务商当前记录和各路径观察值，见 C01、C15 |
| G“被墙”（第 87 行） | 将所有有效点失败写成 IP 状态，但实际只验证特定端口和有限路径；无点推定也被混成同一证据强度 | 高 | 保留产品名称，补充证据来源、端口、时间、覆盖与“无点推定”；不宣称已证明封锁原因，见 C12 |
| G“国内检测点”（第 98 行） | 对照站点成功被表述为“证明自身网络正常”，范围过强；国内正常、跨境异常时仍可能误判 | 中 | 改为“本轮满足对照条件的检测点”；有效性绑定时间窗和任务，见 C13 |
| G“隧道传输”（第 65 行） | “面板自动签发”不精确对应已确认的“每出口生成自签证书”；只信任该证书与额外加入系统根不同 | 中 | 明确每出口自签身份、专用信任范围；保留“WS + PSK 加密”，补协议规格引用，见 C10 |
| G“目标/目标切换”（第 17、52 行） | 未说明域名 IPv4 多答案、当前目标的作用域，跨出口可能有不同答案与健康 | 中 | 目标为配置地址与端口，解析端点与运行选择另列；策略和执行方见 Q06 |
| G“出口策略/后备出口组”（第 39、42 行） | 最小连接数未写统计范围；后备引用边界不明，可能形成循环 | 中 | 策略补“新业务连接的选择方式”，统计范围见 Q07，引用约束见 C17 |
| G“换 IP”（第 106 行） | 未表达被墙节点自己执行；“操作完成”容易混同 HTTP 成功、地址变化和可达恢复 | 中 | 区分请求、执行未知、地址已变、恢复已验证；执行方为节点，面板负责授权协调 |
| G“探针”（第 81 行） | 简略定义容易与国内检测点及检测端口混用；“带宽”可能被理解为购买带宽而非速率 | 低 | 资源采集、国内反向检测角色、检测监听端口分开；带宽改为网卡收发速率，补其余已确认指标 |
| 尚缺术语 | “主入口/首选入口、健康备用、在线、就绪、同步正常、恢复稳定”可能在不同模块被各自解释 | 中 | 在线指控制链活性，就绪指配置/监听等条件；首选与活动分开；其余关联 Q01、Q05、C05、C14 |

ADR 0001 与 gRPC、推送加全量同步的决定一致，缺的是协议契约，不需要因此推翻技术选型。ADR 0002 与决定 12 一致；无检测点时的推定依据仍来自节点自测，不等于引入第三方自动判定，不能把它误报为违反 ADR。

调研中的“增加 TOTP、公共证书优先、仅 WSS、离线继续自行换 IP、解析异常触发切换”等旧建议，不是本项目已确认行为。本审查不将未采纳这些建议视为缺陷。

## 四、v1 范围与建议的交付顺序

**范围偏大，原因是组合状态多。**两种链路、两种隧道传输、两种出口策略、三级切换、三种被墙处理、两家 DNS、自动换 IP 和双端升级需要交叉验证；单项完成并不等于整个闭环可靠。建议按以下切片推进，是否缩减最终 v1 仍由用户决定，以下不是实施授权。

| 切片 | 可独立交付的内容 | 最低验收边界 |
|---|---|---|
| 1. 可管理的直连 | 内嵌前端、密码会话、SQLite、节点安装、经 TLS 代理的 gRPC、版本化同步；单成员入口组、固定端口、单目标 TCP/IPv4 | 配置成功/失败可区分；面板断线后继续转发；重连不恢复已删除规则；重启可恢复有效缓存 |
| 2. 可用的单出口隧道 | 每出口自签 WSS、节点对令牌、逐流授权、yamux、固定出口；基本流量和连接数 | 错证书/错令牌/越权目标被拒；已有连接不因普通配置同步被无故重建；资源有上限 |
| 3. 节点本地容灾 | 有序主备目标、出口主备、真实握手健康、已定失败/恢复窗口 | 区分出口故障与目标故障；失联仍可切换；全故障无循环、不绕过隧道、不重放业务 |
| 4. 只观察的运维闭环 | 资源实时值及分钟历史、国内检测点、自测、事件和 Telegram、DNS 只读监控 | 不确定结果可见；旧 IP/旧版本结果无效；离线事件补报去重；通知不阻塞控制 |
| 5. 受控入口发布 | 多成员入口组、先接一家 DNS、统一动作状态、入口切换/回切、DNS 偏差写回 | DNS 写入超时和面板重启可恢复；传播与失败分开；全入口不可用及并发手动操作有明确结果 |
| 6. 自动换 IP | 自定义 HTTP、执行许可、持久化保护；先仅换 IP，再联动策略③ | 超时不重复申请；真实业务端点变化可确认；无点验证、额度用尽、换后无改善均能停在可解释状态 |
| 7. 运维与功能补齐 | 单节点升级/回滚，再串行批量；第二家 DNS、最小连接数、后备组、WS 加密、随机端口、JSON、itdog 表格/地图 | 升级兼容新旧版本，未确认能停批次；每项有独立失败边界；第三方拨测无法影响自动动作 |

建议优先后移的部分：**itdog 网页模拟与地图、第二种隧道传输、最小连接数与复杂后备组合、批量升级、非必要的完整历史展示**。先保留一种安全隧道、一种出口主备和人工运维兜底；分钟历史采集和升级兼容的接口可预留。后移属于范围调整建议，不是擅自删除已确认需求。

可以后移界面和复杂策略，**不能后移**控制链 TLS 与权限边界、配置版本与应用确认、自动动作幂等/未知状态、端口冲突校验和关键状态持久化。它们决定基础切片是否可信。

## 五、进入实施前应验证的故障场景

本次没有运行测试。后续验收至少应覆盖下列组合，避免仅验证正常路径：

1. DNS 写入已成功但响应丢失，随后面板重启；旧解析采样迟到，不能改回旧入口。
2. 换 IP 已执行但 HTTP 超时，节点重启/控制断开；不能再次申请，重连后恢复同一任务观察。
3. 策略③切备用后，所有国内检测点失效；新 IP 变化不能被误当成国内验证通过。
4. 节点仅能连国内对照站点、不能出境；同轮有效集合变化、缺报及自身被测均有明确结果。
5. 全部入口被墙、全部出口故障、后备关系成环、同节点跨组策略冲突，不发生无限动作或未授权直连。
6. 旧 TTL 较长、残留 AAAA、供应商返回成功但递归仍旧值；不误称污染、不抢写其他记录。
7. 出口换 IP 时部分入口离线，另有证书/令牌轮换；应用进度和可用路径能如实展示。
8. 节点批量升级遇到回连失败、转发失败、面板失联；回滚与“未确认”不混淆，不继续升级最后可用备用。
9. 离线流量/事件重传、节点计数重置、磁盘满、历史清理、旧备份恢复，不能重复累计流量、绕过额度或盲目改 DNS。
10. 错误节点身份、错证书、越权目标、被撤销的已有流及恶意 HTTP/itdog 返回内容，均不能越过相应信任边界。

下一步：先逐项确认 Q01—Q09，优先解决离线执行方、无点回切、跨组换 IP 和回切窗口；再把选定边界并入现有正式设计，按切片推进。更新设计或实施代码均需用户另行明确授权。

本节是写规格（`/to-spec`）时的依据：确定的问题全部采纳为规格要求，下表只注明与原建议不同或被决定改变的地方；未列出的按原建议写入规格。术语见 `GLOSSARY.md`，决定见 `docs/adr/0003`—`0006`。

| 原决定 | 修改后 |
|---|---|

| 编号 | 决定 |
