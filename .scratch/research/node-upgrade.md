对于“Go 面板 + Go 节点、gRPC 双向流、管理员自用、仅 Linux amd64 + systemd”的新项目，建议采用以下取舍。这些是设计建议，不是两个参考项目已经实现的功能，也不是实施授权。

1. **由面板提供固定版本升级包。** 每次发布把面板、`agent-linux-amd64`、版本清单一起打包，由面板通过 HTTPS 提供节点二进制；gRPC 只下发任务 ID、目标版本和清单信息。节点升级到面板明确支持的版本，避免节点各自追逐 GitHub latest。只支持 linux/amd64，省去多架构矩阵和多下载源自动回退；GitHub 可作为管理员获取发布包的来源。

2. **真正验证 SHA256，并使用发布签名。** 清单至少包含目标版本、固定平台、文件大小、SHA256、兼容协议范围；发布时签名，节点内置验证公钥。先验证清单签名，再验证二进制摘要，最后执行候选版本/自检命令。这样即使经面板或缓存分发，仍能验证发布身份；仅从同一个地址取二进制及摘要不能提供同等保证。

3. **借鉴 A 的独立更新服务，用 Go 实现小型更新器。** 节点以普通账户运行，root 所有的 systemd oneshot 更新服务负责安装；节点只写严格受限的任务文件。更新器只接受固定安装路径、合法版本和固定资产类型，不接受任意 Shell 命令。这样符合现有 Go 技术栈，也让更新任务能在节点服务被停止后继续执行。

4. **先完成下载验证，再进入短暂停服窗口。** 建议顺序为：下载暂存 → 验签/摘要/候选自检 → 保留旧程序 → 同文件系统原子切换 → systemd 重启 → 本地健康检查 → 新进程通过 gRPC 确认。启动或本地转发自检失败就恢复旧程序并重启；面板暂时不可达时保留“待确认”，避免仅因网络故障反复回滚。升级器异常退出后，也应能依据持久化阶段恢复或人工重试。

5. **把“服务已启动”和“升级成功”分开。** 持久化任务 ID、目标版本、阶段、错误、旧版本和重启后的进程标识。新版节点回连、实际版本匹配且健康通过后，面板才显示成功；回滚则明确显示“已回滚”。没有结果显示“超时/待确认”，保留失败信息，不能通过清除升级标记表达成功。界面先提供真实阶段进度，有下载字节数据时再显示百分比。

6. **独立维护软件版本、控制协议版本和功能能力。** 节点握手报告三者；面板声明最低协议及功能要求，新增 protobuf 字段保持向后兼容。对仍能安全认证和解析基础消息的旧节点，尽量保留升级控制通道，暂停其不支持的功能；完全无法通信的旧节点才要求重跑安装器。通常先升级兼容旧节点的面板，再升级节点，最后启用新功能。

7. **管理员自用先做手动单节点升级，批量采用串行或很小并发。** 每台确认成功后再处理下一台，比固定时间同时推进多波更容易排障。面板检查到新版本只提示，不默认自动安装。若节点本身承载转发，应明确接受重启造成连接中断；保留配置与计数不等于保留 TCP/UDP 会话，第一版不必引入连接交接和复杂热升级。

8. **面板自身先使用外部 CLI 升级入口。** 复用下载验证、原子替换和 systemd 管理；涉及数据库迁移时，用数据库支持的方式先备份，并明确数据恢复条件。只有数据库及节点状态格式兼容时才自动回滚二进制；不要把“保留旧文件”当成完整数据库回退。面板升级和节点升级保留独立任务与确认过程。
