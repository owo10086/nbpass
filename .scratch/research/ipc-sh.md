这套脚本的核心是：**本机连接多个网站，持续异常后调用外部接口换 IP，再确认出口 IP 变化和连通性恢复，并用持久化计数限制换 IP 频率。**

项目业务文件仅阅读了 [ipc.sh](/Users/macmini/Documents/Aixiaoji/ip被墙自动换/ipc.sh)，未读取任何 `.py` 文件、未修改文件、未执行脚本或调用接口。脚本没有引用其他 `.sh` 或外部配置文件。

## 1. 总体流程

1. **启动检查**：检查 `timeout`、`getent`、`curl`、`flock` 是否存在。
2. **获取进程锁**：已有实例运行时，当前实例退出。
3. **读取历史状态**：恢复上次换 IP 时间、连续无改善次数、最近 24 小时请求记录；状态文件无效则停止启动。
4. **发送 Telegram 启动通知**，随后进入常驻循环。
5. **检测四个网站的 TCP 连通性**：
   - 任一目标解析失败：本轮结果为“未知”，不换 IP，并清零连续异常轮数。
   - TCP 失败目标少于 3 个：本轮通过，清零连续异常轮数及无改善次数。
   - 至少 3 个目标 TCP 失败：累计一轮异常。
6. **连续 3 轮异常后**，检查冷却时间、小时／日配额、无改善暂停条件。
7. **查询换前公网 IPv4**；获取失败则取消本次换 IP。
8. **先增加换 IP 计数并保存状态**；保存失败则禁止调用换 IP 接口。
9. **发送开始通知，调用换 IP 接口**。
10. 接口成功后，**定期查询公网 IPv4，等待它与旧 IP 不同**。
11. IP 变化后，**重新检测网站连通性**：
    - 任一轮通过：宣布成功，清零无改善次数。
    - 连续 3 轮仍异常：通知失败，保留无改善次数，本轮不继续换。
    - DNS 异常：结果未知，保留无改善次数。
12. 本轮结束后等待 120 秒，再继续检测。

入口和主循环见[源码](/Users/macmini/Documents/Aixiaoji/ip被墙自动换/ipc.sh:566)。

## 2. 被墙检测

### 检测位置与方向

检测由**运行脚本的机器主动向目标网站建立连接**。

- 没有国内探针访问节点的逻辑。
- 没有第三方“是否被墙”检测 API。
- **推测**：若脚本部署在国外服务器，就是国外服务器主动连接这些网站；仅凭文件无法确认实际部署位置。

因此，它检测的是运行机器的**出站 TCP 连通性**，不能直接证明国内用户能否连接这台服务器的入站服务端口。

### 检测目标与方法

目标为：

- `tool.lu`
- `www.jikexueyuan.com`
- `www.ui.cn`
- `www.woshipm.com`

脚本将它们作为检测目标，但没有验证目标服务器的实际地域或运营商。

虽然变量名叫 `PING_TARGETS`，实际方法是：

1. 使用系统 `getent ahostsv4` 获取目标 IPv4 地址。
2. 最多选择两个不同的 IPv4 地址。
3. 使用 Bash `/dev/tcp` 尝试连接 **TCP 443**。
4. 只判断 TCP 连接能否建立，**不发送 HTTP 请求，不验证 TLS，也不使用 ICMP ping**。

### 判定规则

| 层次 | 实际规则 |
|---|---|
| 地址解析 | 最多 2 次，每次超时 10 秒 |
| 单目标 TCP 检测 | 最多 3 轮，每轮依次尝试最多两个地址 |
| 单次 TCP 连接 | 超时 5 秒 |
| 单目标正常 | 任意一次连接成功即可 |
| 单目标 TCP 失败 | 所有 TCP 尝试均失败 |
| 单轮异常 | 四个目标中至少 3 个 TCP 失败 |
| DNS 异常 | 任意目标解析失败，整轮直接判为“未知” |
| 触发换 IP | 连续 3 轮异常，且保护条件允许 |

这是**多个目标参与阈值判定**，不是多个地域或运营商探针投票。

### 已有的防误判措施

- 多目标阈值，避免一个网站故障就换 IP。
- 同一目标可尝试两个地址，并重试连接。
- 要求连续 3 轮异常。
- DNS 失败独立处理，不作为换 IP 依据。
- 换前必须成功获取并校验当前 IPv4。
- 换后同时确认“IP 已变化”和“检测恢复”。

## 3. 换 IP

**无法从这个文件确定云厂商。** 脚本没有 AWS Lightsail、EC2、Vultr 等厂商 SDK、API 签名或资源操作代码。

它只调用：

```text
GET http://100.100.101.101:8002/changeip
```

具体行为是：

1. 创建临时文件保存响应。
2. 用 `curl` 发起请求，总超时 60 秒。
3. 同时满足 **curl 退出码为 0、HTTP 状态码为 2xx**，才认为接口调用成功。
4. 保存 HTTP 状态码、curl 退出码、响应体，供通知使用。
5. 随后通过公网 IP 查询确认实际变化。

**响应体没有业务解析**，例如不会检查 JSON 中的 `success` 字段。

该请求没有显式传递鉴权头、实例 ID、区域或其他业务参数。脚本也没有云厂商凭证配置。

申请新 IP、绑定新 IP、解绑或释放旧 IP的顺序，均隐藏在外部接口之后，**本次允许阅读的源码无法确认**。

接口实现见[源码](/Users/macmini/Documents/Aixiaoji/ip被墙自动换/ipc.sh:328)。

## 4. 换 IP 之后

### 确认公网 IP 变化

依次使用：

1. `https://ifconfig.me/ip`
2. 失败后使用 `https://api.ipify.org`

查询强制 IPv4、禁用代理；每个地址连接超时 5 秒、总超时 15 秒。

返回值去除空白后，检查是否符合 IPv4 格式。**这只是格式校验，没有验证地址一定属于全球公网地址。**

换后每隔 60 秒查询一次，最多 5 次；得到有效且不同于旧值的 IPv4，就进入连通性复检。

### 复检规则

最多检测 3 轮，异常轮之间等待 120 秒：

- **任一轮通过就认定恢复**，不要求连续多轮正常。
- “通过”仍指 TCP 失败目标少于 3 个，不要求四个网站全部成功。
- 三轮都异常，认定新 IP 持续异常。
- 任一轮 DNS 异常，则暂不确认结果。

### DNS、通知和配置同步

- **DNS 更新**：本文件没有任何 DNS 服务商 API 调用。
- **通知**：通过 Telegram Bot `sendMessage` 发送启动、开始换 IP、成功、失败及保护告警。
- **其他同步**：没有节点配置、面板记录、订阅地址、证书或转发规则同步逻辑。
- 外部换 IP 接口是否承担上述操作，无法确认。

换后复检见[源码](/Users/macmini/Documents/Aixiaoji/ip被墙自动换/ipc.sh:545)。

## 5. 调度方式与保护

| 项目 | 实际行为 |
|---|---|
| 调度 | 常驻 `while true` 循环 |
| 普通检测间隔 | 每轮执行完后再等待 120 秒 |
| 连续异常要求 | 3 轮 |
| 换后等待 | 每隔 60 秒查询 IP，累计等待 300 秒 |
| 冷却时间 | 两次换 IP 请求至少间隔 1800 秒 |
| 小时限额 | 滚动最近 3600 秒最多 1 次 |
| 日限额 | 滚动最近 86400 秒最多 3 次 |
| 连续无改善上限 | 2 次，跨轮、跨重启保存 |
| 暂停解除 | 后续检测出现正常结果，清零无改善次数 |
| 并发保护 | 主进程全程持有本机文件锁 |

需要注意：

- **不是固定每两分钟开始一轮**，实际间隔还包含检测、通知及换 IP 耗时。
- `MAX_CHANGE_ATTEMPTS=2` **不是本轮连续重试两次**。每轮最多发起一次请求，后续还要经过检测和限频。
- 达到无改善暂停条件后，**不会仅因等待足够长而自动解除**。
- 以当前配置，小时限额比 30 分钟冷却更严格。
- 文件中没有安装 cron、systemd 或自动重启服务的逻辑。
- `--check` 模式只执行单轮检测，不换 IP、不通知；返回码为正常 `0`、异常 `1`、未知或缺依赖 `2`。

限额实现见[源码](/Users/macmini/Documents/Aixiaoji/ip被墙自动换/ipc.sh:206)。

## 7. 失败处理与边界情况

| 情况 | 实际处理 |
|---|---|
| 任一目标 DNS 失败 | 整轮未知，清零连续异常轮数，不换 IP |
| 换前公网 IP 查询失败 | 告警，不请求换 IP，也不消耗换 IP 配额 |
| 保存换 IP 计数失败 | 禁止调用接口；已经增加的内存计数不回滚 |
| 接口超时、HTTP 非 2xx、curl 失败 | 通知失败，已占用的配额及无改善次数保留 |
| 接口成功但公网 IP 未确认变化 | 通知失败，本轮结束 |
| 新 IP 仍异常 | 保留无改善次数，后续受限频和暂停条件控制 |
| 换后 DNS 异常 | 不确认成功，保留无改善次数 |
| 状态文件无效或不可读 | 停止启动 |
| 状态文件不存在 | 按零历史启动 |
| 第二个实例启动 | 获取同一锁失败后退出 |
| Telegram 发送失败 | 没有可靠投递确认、重试或补发 |

另有几个细节：

- **接口失败后不会再确认 IP 是否其实已变化。** 因此可能出现后端已经执行、响应却丢失的情况；这是由调用流程推导出的边界风险。
- **300 秒不是严格总超时。** 代码只累计 `sleep` 时间，不包含公网 IP 查询；按配置推算，等待阶段可能接近 450 秒。
- **恢复状态保存失败处理不完整。** 内存无改善次数先清零，再保存；保存失败只记录警告，调用方仍可能发送成功通知。重启后会读回旧计数。
- 文件锁只约束使用同一锁路径的本机进程，不协调多台机器请求同一个换 IP 后端。
- 请求计数会持久化，但连续异常轮数和通知去重状态不会跨重启保留。

## 8. 弱点与值得改进的地方

以下是**评估及改进建议，不是脚本已有功能**。

1. **检测方向与真实服务可用性有差距。**  
   本机能否连接网站，不能直接代表国内用户能否连接节点。新项目更适合由国内不同运营商的探针检测节点实际服务端口，并结合节点自身健康状态、境外对照结果区分故障原因。

2. **“被墙”只是连通性异常的解释之一。**  
   线路故障、网站故障、节点防火墙或本机网络异常，都可能触发当前阈值。四个域名也不等于四个独立地域或运营商。

3. **DNS 保护很保守，恢复确认较宽松。**  
   一个目标 DNS 失败就使整轮未知，可能长期阻止换 IP；另一方面，只要一轮失败目标降到 2 个，就认定恢复。重写时可以区分“未知、部分异常、持续异常、持续恢复”等状态。

4. **换 IP 接口缺少可追踪的操作状态。**  
   当前使用明文 HTTP，调用没有显式鉴权、幂等键或任务 ID。Go 版本可将换 IP 设计为可查询状态的操作，明确记录申请、绑定、验证、释放各阶段，处理超时后的结果不确定问题。

5. **换后验证范围有限。**  
   仅确认出口 IPv4 变化和网站连通性，没有验证节点实际服务、域名解析或旧 IP 回收情况。新项目应根据真实访问路径完成验证。

6. **保护机制值得保留，但需要更完整的失败闭环。**  
   “请求前保存计数、滚动限额、跨重启暂停、单实例锁”都有参考价值；可进一步完善状态保存失败处理、通知重试、配置校验及严格总超时。

下一步：先明确新项目采用的云厂商、节点实际服务端口和国内探测来源，再据此设计 Go 版本的检测与换 IP 状态机。
