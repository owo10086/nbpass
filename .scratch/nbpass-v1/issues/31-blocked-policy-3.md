# 31: 被墙策略③（先入口切换，再换 IP，复检通过后切回）

**What to build:** 策略③下，活动入口被认定被墙时，先切到就绪的备用成员，再给原节点换 IP；新 IP 复检恢复后，按回切规则切回首选入口；自动回切已暂停时不切回。没有就绪备用成员时退化为策略①；换 IP 失败、受限、待确认或冻结时留在备用成员并通知。管理员手动切换会提高期望版本，使进行中的策略③切回失效。

**Blocked by:** 25, 27, 30

**Status:** ready-for-human

**Refs:** 规格用户故事 66a（作废部分）、77（策略③部分）、78、79；必测场景 3；规格「被墙处理策略状态」

- [x] 完整流程：切走 → 换 IP → 复检通过 → 回切，假 DNSPod 记录值依次正确
- [x] 没有就绪备用成员时直接换 IP，换成后记录更新为新 IP
- [x] 复检始终异常时留在备用成员，无改善累计，2 次后暂停并通知
- [x] 额度用尽或冻结时留在备用成员并通知
- [x] 策略③进行中，管理员手动切换后，原切回请求作废
- [x] 以上行为由测试台通过面板 HTTP API、假换 IP 接口与假 DNSPod 验证

2026-11-09 实施记录（分支 `ticket/31`，仅在指定工作目录实施；未创建工作树，未修改 docs/、其他票或节点上报处理）：

- **先切后换**：开放入口组策略 `switch_then_rotate`，沿用票 27 的被墙事故、候选检查、`entryMu → controlMu` 与 `submitEntryActionTx`。同一事务保存切离动作和策略③工作流；必须由原协调器确认切离动作及当前发布均已写入，才获得本组自动换 IP 资格。DNSPod 不可用、提交失败或响应丢失未核对时不能调用商家；不等待传播完成。没有就绪备用时持久保存退化决策，直接申请策略①的节点换 IP，确认新地址后仍由协调器更新当前受管记录。策略①、②沿用原行为。
- **统一授权与恢复**：只扩展既有自动申请资格；执行、在线/能力、自动总授权、维护、恢复核对、冷却、节点共享额度、无改善暂停及冻结仍走票 30 的 `authorizeRotation`。许可与工作流的动作关联同事务落库，重启不丢关联、不重复调用商家。三轮无改善后可在共享额度释放时重试，连续两次无改善由原策略暂停；待确认、取消、结果未确认时不盲重试。管理员合法手动节点换 IP 可接续当前有效工作流，仍走原节点互斥与计费规则。
- **复检与回切**：仅本工作流关联动作的 `changed/recovered` 且新 IP 与节点当前地址一致，才开始累计票 25 的回切窗口；周期正常自测不能代替本次复检。六次连续候选成功、两分钟驻留和手动暂停规则均保留，提交事务再次复核。手动入口切换提高期望版本，使旧工作流的后续自动许可申请和回切失效；同活动入口的自动 `writeback/address_update` 延续当前恢复门槛，不能借自动修复版本跳过复检。工作流只抑制本组当前活动节点的重复事故，不阻挡备用入口再次真实故障。
- **事件与界面**：策略③可在入口组设置中选择并保存，说明先切后换、无备用退化、共享限制和手动切换作废。沿用持久换 IP 事件/Telegram 待办，对无改善、待确认、冻结、取消或授权受限补充本组影响，明确切离后留在备用；通知按决策、动作与阶段去重，关联键用固定长度摘要，兼容队列长度限制。事件页新增“策略③等待恢复”。策略②等待期间改选③使用独立决策键，避免复用“不换 IP”的旧说明。
