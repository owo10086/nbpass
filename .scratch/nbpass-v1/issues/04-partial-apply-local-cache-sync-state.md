# 04: 部分应用语义、节点本地缓存与同步状态

**What to build:** 节点逐规则报告实际生效的规则版本和错误（例如端口实际 bind 失败）；"已应用版本"只在整个快照全部应用成功后推进。节点持久化实际生效状态，启动先加载缓存再连接面板，与面板失联时按缓存继续转发。每条规则显示同步状态（未同步、正常、同步失败、待确认），可展开看每个成员节点；失联节点显示待确认。测试台增加"保留磁盘重建节点或面板核心"的生命周期能力。

**Blocked by:** 03

**Status:** ready-for-human

**Refs:** 规格用户故事 20、21、32；必测场景 15（部分应用部分）；规格「控制服务·部分应用语义」「节点模块·控制客户端与本地缓存」；ADR 0006

- [x] 端口被外部进程占用时，该规则显示同步失败及具体节点、端口和原因，同一快照中的其他规则正常生效
- [x] 部分成功时已应用版本不推进；规则和入口组的汇总只要有成员失败或待确认就不显示正常
- [x] 控制链路断开后节点继续按缓存转发；节点重启后先加载缓存恢复监听
- [x] 部分应用失败后重启，已停用或删除的规则不复活
- [x] 失联节点的同步状态显示待确认，不显示正常
- [x] 测试台支持保留磁盘重建节点核心和面板核心
- [x] 以上行为由测试台通过面板 HTTP API 与真实 TCP 验证

## Comments

2026-11-09 实施记录（分支 `ticket/04`，仅在当前工作目录实施）：

- **逐规则实际结果**：`forwarding.Engine` 为快照中的每条规则记录实际生效版本和监听错误，未变化的规则保留监听及业务连接。一个规则 bind 失败不阻止其他规则；整个快照全部成功且实际结果落盘后才推进节点已应用版本。监听错误包含规则、端口及具体原因，汇总与逐规则错误按完整 UTF-8 字符截断，并共享控制消息预算，避免多规则失败超过 64 KiB 后整份报告丢失。
- **缓存与撤销顺序**：新增独立 `node.ConfigStore`（`LoadConfig/SaveConfig`），标准 `FileStore` 自动启用，定制凭据存储可实现该接口或通过 `Dependencies.ConfigStore` 注入。配置缓存 `config.enc` 复用本机密钥，以独立 AES-GCM 关联数据加密；目录 0700、文件 0600，临时文件同步、原子替换及目录同步，读取上限 2 MiB，拒绝不安全权限、符号链接和损坏密文。缓存格式版本为 **1**，绑定节点 ID 与控制地址，独立保存快照高水位/摘要、最后完整成功版本/摘要、实际生效规则及逐规则结果。
- **部分失败与重建**：应用前先持久化不含已删除、停用或变化旧规则的撤销检查点，再撤销运行时规则，最后持久化实际成功结果。检查点失败时不执行撤销，并显示失败；最终写盘失败时不推进整体版本，重启只恢复检查点中的实际规则，已撤销规则不会复活。节点启动先从缓存重新 bind，随后连接面板；缓存恢复的 bind 失败会清除本进程的完整成功确认。失败而未生效的期望规则不会在离线重启时自行启用；恢复控制连接后用当前完整快照重试。不设置离线授权期限。
- **协议与报告独立性**：控制协议仍为版本 1，新增 `NodeReport.rule_results = 20`、`attempted_digest = 21`、`revocations_applied = 22`；新增消息 `RuleApplyResult` 的字段为 `rule_id = 1`、`applied_revision = 2`、`apply_error = 3`。`PanelMessage` 未增字段。protobuf Go 源码由 `make proto` 生成。逐规则与撤销确认只由配置报告推进；探针、事件及活性互不推进对方状态。新进程先使旧报告确认失效，历史实际规则仅供展示待撤销明细；旧流、旧实例、旧/超前版本、错误摘要及迟到失败不能覆盖当前确认。对上一版节点保留无摘要的节点级失败报告兼容；完整成功的摘要确认可补齐逐规则正常状态。
- **迁移与 HTTP API**：在基线版本 7 之后追加 **迁移 8**（合并时可重排），新增 `node_rule_reports`、`node_rule_results`。节点整体状态、逐规则结果与撤销确认在同一事务保存。`GET /api/rules` 新增 `sync_status`、`sync_members`；每个成员含节点 ID/名称、控制连接、监听端口、期望/实际生效版本、同步状态及错误。`GET /api/entry-groups` 同样提供汇总及逐成员、逐规则明细；保存历史实际归属和端口，让删除、移组及节点重启后的未完成撤销仍可见。确认撤销后清理历史明细。查询只在构造内存视图时持控制锁，HTTP 写出时不持锁。
- **汇总与范围决定**：同节点其他入口组的错误不污染本组；失联成员一律显示“待确认”。多种成员状态同时存在时按“同步失败 > 待确认 > 未同步 > 正常”汇总，并保留全部成员明细；单个失联成员不沿用旧失败作为当前确认。停用规则显示正常表示监听已确认撤销。入口组写入仍沿用票 03 的单成员限制，查询和汇总按成员集合实现，留给后续多成员票扩展；不实现 DNS、就绪候选、静态端口预检或资源限制。无阻塞实施的开放问题，无规格行为偏离。
- **页面与生命周期**：规则及入口组页面新增同步列、逐成员展开与错误/版本信息，每 10 秒刷新；启停请求显式选择规则输入字段，不把只读同步结果提交给严格 JSON API。沿用测试台 `Node.Restart()`、`Harness.Restart()`：保留磁盘和外部依赖，重建真实引擎、进程实例、探针与持久队列；新增真实离线重建验收。票 03 的新进程测试按“先恢复缓存、再建控制连接”的新顺序更新，恢复完成前必须显示待确认。
- **TDD 与复核**：新增 **13 个顶层测试**（8 个测试台场景、5 个包内物理/协议场景）。业务操作和同步断言均通过面板 HTTP API，数据面使用真实 TCP，节点为真实 `node.Run`。覆盖外部端口占用、同快照部分成功、入口组隔离、整体版本不推进、失联转发、节点/面板保留磁盘重建、停用/删除不复活、两阶段写盘失败、缓存监听失败、删除/移组/重启后的待撤销明细、高水位防回退、报告隔离、缓存加密/权限/格式/身份与消息预算。规则缺少同步视图、撤销检查点失败误报正常、错误摘要污染节点汇总、删除/移组/新进程丢失撤销明细均先观察到 RED 再修复；另暂时关闭缓存恢复，确认离线重建测试确实失败后恢复并转绿。只读复核提出的上述问题已关闭，最终无剩余阻塞项。
- **最终验证与产物**：`env -u FORCE_COLOR make test` 全绿（npm ci、TypeScript/Vite、节点包重建、go vet、全仓 go test）；`go test -race ./... -count=1` 全绿；面板与节点均经 `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath` 交叉编译，`file` 确认为静态链接 x86-64 ELF；`git diff --check` 通过。Vite 沿用已有的 AntD 大包非阻断提示。提交前按并行规则还原 `web/dist`、`internal/nodebundle` 并移除本轮新增前端产物；**本票依赖合并后统一重新生成前端和内嵌节点包**，请运行 `make build` 或相应构建目标。

人工验收清单（尚未执行，页面验收复选框保留未勾选）：

1. 合并并重排迁移后执行 `make build`，通过可信 HTTPS 反向代理登录，接入真实 Linux amd64 节点。打开转发规则和入口组，在桌面及窄屏检查同步列、展开/折叠、成员名称、端口、期望/实际版本、错误换行及自动刷新；新建、编辑、启停与删除仍可操作。
2. 在节点上用外部进程占用一个规则监听端口，再为同一节点配置该规则及另一条可用规则。确认失败规则指出具体节点、端口及 bind 原因，另一条规则真实转发正常；整体已应用版本停留在上次完整成功版本，本组汇总失败，同节点不受影响的入口组正常。
3. 部分失败期间停用一条原有规则并删除另一条；确认监听及已有连接已关闭。阻断控制链路后重启节点，确认剩余成功规则从本地缓存恢复，已撤销规则未恢复监听，页面显示待确认；重启面板后也不能把旧记录显示为正常。
4. 保持控制链路阻断，验证节点继续转发；恢复链路并释放占用端口，确认通过当前快照重试后逐规则、入口组及整体配置版本收敛。另在节点停止时占用缓存规则端口再启动，确认恢复 bind 失败不会沿用旧成功确认。
5. 检查节点缓存目录 0700，`node.key`、`config.enc` 0600 且属服务运行用户；通过 systemd 重启及生产反向代理持续运行，确认控制流和转发均恢复。测试台已覆盖磁盘故障，生产验收无需破坏实际数据目录来模拟磁盘满。
