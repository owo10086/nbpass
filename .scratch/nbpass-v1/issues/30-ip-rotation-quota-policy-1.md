# 30: 换 IP 额度、新 IP 复检与被墙策略①

**What to build:** 换 IP 有节点级额度：冷却 30 分钟、滚动 1 小时最多 1 次、滚动 24 小时最多 3 次，按尝试计数、跨重启保存、同一节点的各种用途共用；查询公网 IP 失败而取消时释放预占的额度。新 IP 用自测复检，最多 3 轮，任一正常轮即"已恢复"；3 轮均为有效异常记一次"无改善"，没有正常轮但含未知轮记"待确认"、不累计。连续 2 次无改善后暂停自动换 IP 并通知，之后出现正常自测轮或管理员手动解除即可恢复。策略①下，节点被认定被墙即自动换 IP，换成后协调器把受管记录更新为新 IP。手动换 IP 不受冷却和次数限制，但计入额度。

**Blocked by:** 18, 22, 29

**Status:** ready-for-human

**Refs:** 规格用户故事 77（策略①部分）、92、93、94、96（受管记录部分）、98、98a、114（被墙与换 IP 部分）；必测场景 3（无改善部分）、16（手动部分）；规格「换 IP 授权」

- [x] 完整流程：被墙 → 自动换 IP → 假 DNSPod 记录为新 IP → 复检通过 → 已恢复，全程有事件和通知
- [x] 30 分钟内的第二次自动换 IP 被冷却拦下；滚动 24 小时内的第 4 次被拦下；面板重建后额度不丢
- [x] 复检始终异常时记无改善，2 次后暂停并通知；复检全部未知时记待确认、不累计
- [x] 手动解除无改善暂停或冻结后自动换 IP 恢复，已用额度不清空
- [x] 冷却期内手动换 IP 仍能执行，执行后计入额度
- [x] 节点离线时不签发许可
- [x] 以上行为由测试台通过面板 HTTP API、假换 IP 接口与假 DNSPod 验证

## Comments

2026-11-09 实施记录（分支 `ticket/30`，仅在指定工作目录实施、提交；未创建工作树，未修改 docs/ 或其他票）：

- **额度与迁移**：在第 20 版之后追加 **迁移 21 `rotationPolicyMigration`**，合并时可重排。新增独立于可清理事件历史的 `rotation_quota`、`rotation_policy`，扩展动作的来源、许可投递标记、复检配置/版本/证据/状态，增加节点自动总授权与入口组策略。旧非取消动作保守回填尝试记录，保留原动作、冻结、序号与入口组自动回切暂停；旧动作标记为可能已投递，不虚构复检结果。物理升级回归覆盖真实第 20 版数据库到第 21 版。
- **统一授权**：手动与自动共用 `authorizeRotation`，节点级串行预占，按授权尝试时间统计滚动窗口 `(now-window, now]`；自动受 30 分钟冷却、1 小时 1 次、24 小时 3 次、暂停、冻结、维护、在线与网络风险约束。手动绕过冷却/次数/无改善暂停，但仍与进行中、复检中、结果未确认动作互斥，并计入同一额度。执行前取消（包括公网 IP 查询失败）释放预占，外部调用开始后的不确定结果保留额度。手动解除暂停或冻结均不删除额度。
- **策略①与 DNS**：默认节点自动总授权关闭、入口组策略 `disabled`；管理员需配置换 IP 接口、开启节点自测与自动总授权，并将关联入口组设为 `rotate_ip`。被墙后后台申请同一节点许可，授权事务内重新确认自测与组策略，避免已停用策略仍签新许可。换成时与节点地址确认同事务提交协调器 `address_update`，只更新当时活动入口仍为该节点且期望值仍为旧 IP 的已发布受管记录；未发布的组不自动首次发布，已切到别处的组不被拉回。沿用 ADR 0005 的唯一协调器、期望版本和 DNSPod 执行路径，节点不写 DNS。
- **新 IP 复检**：命令固定签发时的自测设置与版本，节点复用真实自测执行器，最多 3 轮，首轮立即、后续按该设置的间隔（默认 120 秒）；周期自测关闭也不取消已授权动作的复检。任一正常为 `recovered`，3 轮全异常为 `no_improvement`，没有正常但含未知为 `pending`。未知不增加也不清空连续无改善次数；连续 2 次无改善暂停自动换 IP，持久保存事件和 Telegram 通知待办。复检配置、轮次和下一轮时间写入原加密动作缓存，面板和节点重建后续检，同一动作不重调商家；动作地址与已存证据不能被后续进度覆盖。
- **恢复与乱序**：后续有效原始正常自测或正常检测点补判，均清零连续无改善并解除暂停；管理员也可显式解除。以证据发生时间及手动解除时间为水位：较早正常轮迟到不能清掉较晚暂停，解除前已完成的失败迟到不能重新累计。正常补判即使晚于下一异常轮收到，也会解除无改善暂停，同时保留最新轮的疑似被墙判定。复检本身的未知轮保持待确认，不另行发起检测点补判；后续周期自测仍沿用票 19 的补判机制。
- **协议与兼容**：仅使用分配的 **180–189** 号段：`NodeReport.rotation_recheck_capable=180`；`RotationCommand.recheck_config=180`、`recheck_revision=181`、`automatic=182`；`RotationProgress.recheck_rounds=180`、`recheck_complete=181`。已用 `make proto` 生成 Go 源码。能力只从当前控制会话的活性报告读取；旧节点可继续手动换 IP，确认变更后显示待确认而非卡在复检中，不向旧节点授权自动换 IP。自动许可投递前能力消失则取消并释放；可能已投递则保留原动作/额度、暂停投递，升级节点后核对原动作，避免假定商家未执行。自动动作首次预检发现 NAT/多公网 IP 风险即取消，不调用商家；手动延续原有风险提示行为。
- **API 与界面**：新增 `PUT /api/nodes/{id}/ip-rotation/automatic {enabled}`、`POST .../resume {confirm:true}`、`GET/PUT /api/entry-groups/{id}/blocked-policy {policy:"disabled"|"rotate_ip"}`，沿用管理员认证、同源与严格 JSON 边界。换 IP 视图增加小时/日用量、冷却与额度释放剩余秒数、连续无改善、暂停及复检证据；节点弹窗可操作自动总授权、解除暂停，入口组详情可选策略①，事件增加中文阶段标签，保留票 29 的冻结与核对操作。
- **锁与通知**：地址确认已有 `controlMu`，不能反向获取 `entryMu`（入口保存顺序为 `entryMu → controlMu`）；将协调器提交提取为事务内部接缝，依靠同一数据库事务串行维护期望版本，确定性锁边界回归先失败后修复。通知与动作同事务保存，复用现有持久 Telegram 队列，商家/DNS/Telegram 外网请求不进入许可授权事务。
