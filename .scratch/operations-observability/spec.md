## 1. 目标与范围

本轮按“稳定运维”方向改造：先统一状态判断，再完善首页，最后把检测、入口切换、换 IP、复检、回切和 DNS 传播串成可追查的过程。

完成后，管理员应能回答四个问题：

1. 当前发现了什么异常？
2. 涉及哪些入口组和转发规则？
3. 自动处理已经做到哪一步，为什么停在那里？
4. 是否需要人工介入，应该去哪里处理？

覆盖方案讨论时已实现的主备入口组、直连及隧道规则，以及相关检测、入口切换、换 IP、回切和 DNS 传播。

“全部发布、单节点规则、观测模式”在讨论时已有待实施规格。本方案以讨论时的实际实现为基础，数据结构预留入口对象类型，待这些功能交付后接入同一套运维视图。正式实施前须重新核对仓库状态；若相关功能已经落地，应先更新本文件中的数据来源及适配任务，避免沿用过时字段。新增范围或业务取舍须再次确认。

本轮沿用现有自动处理策略、检测阈值和协调器。新的运维模块负责读取、关联和解释状态，自动动作仍由现有模块执行。

## 2. 状态含义与影响判断

现有证据主要包括控制连接、规则应用结果、监听、隧道握手、自测、国内检测和 DNS 采样。它们尚不能完整证明用户到目标的业务请求是否成功，因此页面采用以下表达。

| 展示状态 | 判断依据 | 典型情况 |
|---|---|---|
| 检测到转发异常 | 当前相关规则存在有效的失败证据 | 活动入口上的规则监听失败 |
| 存在风险或冗余下降 | 当前入口未发现相关异常，但备用能力受损 | 活动入口正常，备用入口无法成为候选 |
| 影响待确认 | 缺少足够、新鲜的证据 | 控制连接中断，但节点可能继续按缓存配置转发 |
| 未发现转发异常 | 当前已有证据未显示异常 | 规则应用、监听及所需隧道证据符合要求 |
| 未启用或待部署 | 当前没有投入使用 | 规则已停用，或入口组尚无启用规则 |

判断必须满足以下规则：

1. **逐条规则判断影响。** 某条隧道规则握手失败，不能直接把同组全部规则判为异常。
2. **区分活动入口和备用成员。** 备用成员失败首先影响冗余能力。
3. **区分期望、服务商确认和解析观察。** 提交切换请求后，不能立即把目标成员当成已经对外生效的入口。
4. **过期证据明确标记。** 展示采样时间、证据来源和待确认原因。
5. **统计按规则 ID 去重。** 同一规则被多个异常关联时，只计一次。
6. **不推测已有连接的存活情况。** DNS 变化不代表已有 TCP 连接已迁移。

没有绑定受管记录的入口组，面板无法判断用户实际连接了哪个成员，应展示成员及规则状态，并说明对外使用情况待确认。

## 3. 首页调整

首页上方展示四项业务关注指标：

| 指标 | 统计口径 |
|---|---|
| 检测到转发异常的规则 | 有当前有效异常证据的启用规则，去重统计 |
| 影响待确认的规则 | 缺少关键证据且未归入明确异常的启用规则 |
| 冗余下降的入口组 | 当前服务入口未发现异常，但备用能力不足 |
| 需要人工介入的故障 | 存在明确人工处理原因的未结束故障 |

节点在线数、启用规则数保留为辅助信息。

首页主体分为三块：

- **当前异常与影响**：原因、相关入口组、相关规则、证据时间、当前处理进度。
- **自动处理进度**：正在检测、正在切换、等待 DNS 传播、换 IP 复检中等。
- **最近结束的故障**：触发原因、采取过的动作、结束方式和持续时间。

同一故障关联多个入口组时，首页显示一个主项，展开查看各组进度，避免一件事刷满列表。

卡片示例：

> **入口 A 被判定被墙 · 关联 3 条启用规则**
>
> 切换到 B 的记录已由 DNSPod 确认写入；国内解析仍有旧地址，传播尚未确认完成。
>
> A 已换成新 IP，正在复检。
>
> 操作：查看处理过程｜查看入口组

“关联 3 条规则”表示依赖关系，是否已有转发异常由逐规则证据另外说明。

## 4. 故障列表与详情

在“监控”导航中增加“故障”。现有事件日志继续保留，供查看原始记录。

故障列表支持以下筛选：

- 进行中、等待人工、已结束；
- 节点、入口组、规则；
- 被墙、离线、配置或监听异常、隧道异常、DNS 异常；
- 起止时间。

故障详情包含：

| 内容 | 展示要求 |
|---|---|
| 故障摘要 | 首次发现时间、当前状态、最新证据、结束方式 |
| 影响范围 | 相关节点、入口组、规则及各自当前判断 |
| 处理时间线 | 检测、决策、动作、确认、复检、传播结果 |
| 当前阻塞原因 | 没有候选、额度不足、结果未确认、等待恢复核对等 |
| 操作入口 | 跳转现有节点、入口组、规则或解析监控页面 |

处理过程按实际策略生成，允许出现分支。例如“切到 B”和“A 换 IP”有各自进度，不能强行排成一个固定步骤条。

人工处理入口继续使用现有操作及确认流程。详情页首先提供定位和解释，避免新增一套可能与原流程冲突的操作入口。

## 5. 故障关联与结束规则

采用“现有业务状态 + 持久化故障记录”的方式。当前状态直接来自现有业务数据，故障记录保存过程、关联关系和当时的影响快照。

### 5.1 关联规则

1. 优先使用现有离线事故 ID、被墙事故 ID、入口动作 ID、换 IP 动作 ID、期望版本和配置版本。
2. 一个节点故障可以关联多个入口组，各组分别记录切换和传播进度。
3. 一个换 IP 动作关联多个组时，只展示一次实际换 IP，并列出相关组。
4. 不通过中文消息内容、相近时间或相同节点名猜测关联。
5. 无法可靠关联的旧事件，保留为原始记录，明确说明关联信息不足。

对配置、监听和隧道异常，使用“对象 ID、规则 ID、配置版本、原因码”识别同一轮异常；恢复后再次发生，创建新故障。

### 5.2 两个独立状态维度

- **异常状态**：仍存在、证据待确认、已解除。
- **处理状态**：处理中、等待条件、需要人工、已结束。

例如，切到 B 后转发侧证据恢复，但 A 仍被冻结，页面可以同时显示“当前转发侧未发现异常”和“原节点仍需人工处理”。

### 5.3 结束方式

| 结束方式 | 含义 |
|---|---|
| 异常解除 | 有符合现有业务规则的恢复证据 |
| 管理员操作结束 | 手动切换等操作使原流程停止或改变 |
| 配置变更结束 | 规则停用、删除或入口关系变化 |
| 新版本替代 | 原处理流程已被新的期望版本替代 |

后三种均不显示为“业务恢复”。单纯经过一段时间，也不能自动宣告恢复。

## 6. 后端结构与接口

讨论时 `internal/panel/http.go` 中的 `GET /api/overview` 仍为空响应，首页由前端分别请求多个接口拼装。改造后由后端提供统一结果，首页和侧栏使用同一份数据。

### 6.1 查询接口

| 接口 | 用途 |
|---|---|
| `GET /api/overview` | 返回统一指标、当前异常和处理摘要 |
| `GET /api/incidents` | 按条件分页查询故障 |
| `GET /api/incidents/{id}` | 查询摘要、影响范围及阻塞原因 |
| `GET /api/incidents/{id}/timeline` | 分页查询处理过程和关联事件 |

响应包含生成时间、证据时间和数据完整性信息。读取失败时返回明确错误；前端保留旧数据并显示最后更新时间，不能把请求失败显示为零异常。

### 6.2 拟新增模块

| 文件 | 职责 |
|---|---|
| `internal/panel/operations_model.go` | 状态、影响范围、原因及摘要结构 |
| `internal/panel/operations_snapshot.go` | 批量读取现有业务状态并构造快照 |
| `internal/panel/operations_evaluate.go` | 根据快照计算展示状态，不发起动作 |
| `internal/panel/incidents_store.go` | 故障、关联、时间线和同步进度的存储 |
| `internal/panel/incidents_projector.go` | 将持久化业务事实整理为故障过程 |
| `internal/panel/operations_api.go` | 概览及故障查询接口 |

### 6.3 存储内容

故障数据至少保存：

- 故障摘要与开始、更新时间；
- 节点、入口组、规则的关联；
- 动作、版本、阶段和证据来源；
- 发生时间与面板观察时间；
- 去重键及投影处理进度。

所有查询复用现有鉴权。新增存储采用追加迁移，沿用现有 SQLite 和时间依赖。

## 7. 可靠性与历史处理

故障整理在后台进行，读取现有持久化状态和事件；页面访问只查询结果。新增展示数据的写入失败，应显示整理延迟并继续重试，不能使入口切换或换 IP 为等待展示记录而停住。

必须满足：

1. 相同事实重复处理只产生一条时间线记录。
2. 面板重启后从持久化进度继续，不重复生成故障。
3. 迟到的旧事件可以补充历史，不能覆盖当前版本的状态。
4. 短暂状态若没有可靠的历史证据，只记录“面板首次观察到”，不补造准确发生时间。
5. 旧数据库升级时，为仍存在的异常建立“升级时发现”记录；不虚构升级前的完整过程。
6. 故障历史保存对象名称快照，节点删除后仍可阅读，且不阻止正常删除节点。
7. 已结束故障沿用事件保留天数；未结束故障保留。
8. 清理后保留必要的处理进度，防止后台再次生成已过期历史。
9. 时间线只保存现有安全摘要、原因码和必要引用。

当前 DNS 传播已有自己的确认规则，运维视图直接使用其结果，不再增加一套“过了 TTL 就认为生效”的判断。

## 9. 验证与验收标准

### 9.1 核心场景

| 场景 | 预期结果 |
|---|---|
| 控制连接中断，节点仍按缓存转发 | 显示控制异常及影响待确认，不直接宣告业务中断 |
| 活动入口正常，备用入口未就绪 | 显示冗余下降 |
| 同组只有一条规则监听失败 | 仅该规则归入明确异常，其余按各自证据判断 |
| 活动入口被墙且无候选 | 显示具体候选不足原因及现有策略实际走向 |
| 切换已提交，DNSPod 尚未确认 | 区分期望入口与最后确认的发布状态 |
| 服务商已写入，DNS 仍返回旧地址 | 显示传播中；超过现有观察窗口则显示传播未确认 |
| 换 IP 成功但复检未通过 | 显示新地址已确认、恢复尚未确认 |
| 换 IP 结果未知或被冻结 | 显示阻塞原因，提供现有核对页面入口 |
| 同一节点关联多个入口组 | 一个主故障、多个组进度；规则计数去重 |
| 故障期间手动切换或修改策略 | 原流程按实际版本结束，旧结果不能覆盖新状态 |
| 面板重启、事件重放或乱序 | 不重复创建，不把已结束故障错误推进 |
| 数据过期、接口失败、无检测覆盖 | 明确显示缺测及最后更新时间 |
| 停用规则或删除关联对象 | 结束方式准确，历史仍可读 |
| 故障整理存储失败 | 运维页面显示延迟，现有自动处理继续运行 |

### 9.2 验证层次

1. **后端行为测试**：状态计算、迁移、关联、去重、恢复和清理。
2. **集成测试**：复用 `internal/clusterharness` 的假时钟、假 DNSPod、假换 IP 接口及节点环境。
3. **页面与 Linux 验收**：检查完整操作路径、刷新失败、窄屏显示及实际部署行为。

实施期间按任务运行相关 Go 测试和前端构建；交付前执行项目完整检查：

```sh
make test
make linux-amd64
```

### 9.3 性能场景

使用 100 节点、1,000 条规则及 10,000 条已结束故障，检查分页、批量查询和后台整理是否拖慢控制报告与配置写入。

请求处理期间不执行外部网络检测，也不按节点逐个查询数据库。

## 10. 交付检查点

1. **状态可信**：后端能正确回答“哪里异常、影响哪些规则”，先核对判断口径。
2. **过程可追查**：通过一轮“被墙 → 切换 → 换 IP → 复检 → 回切”的完整集成场景。
3. **页面可用**：首页、侧栏、故障详情和现有操作入口连通，再完成 Linux 验收。
