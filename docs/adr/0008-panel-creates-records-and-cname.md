# 面板可新建受管记录，主备组可用 CNAME 指向节点记录

ADR 0007 规定面板只接管管理员预先在 DNSPod 建好的 A 记录、不新建也不删除。实际使用中这条边界成本过高：每绑定一个新名字、每给全部发布组加一个成员，都要先去 DNSPod 手动建记录；名字已是 CNAME 时下拉框里根本看不到。参考面板（Forwardx、nekopass、zeroforwarder、RelayX）都是"输入记录名，面板负责建或改"，没有一家要求预建。因此改为：管理员按主机记录名绑定，没有记录就由面板新建，已有就接管；类型不符的同名记录经确认后改类型再接管。仍然不删除记录——删除不可逆，且会误伤管理员在面板外用着的同名记录（Forwardx 的整组同步会删多余记录，我们不跟）。

新建的记录一律先暂停，由现有的首次发布或加回步骤启用。这样记录 ID 在绑定时就存在，"以服务商、域名和记录 ID 标识、全局唯一归属"的模型不变，对外暴露的值也始终经过发布前的就绪检查。

主备入口组可以选 CNAME：组记录 CNAME 到活动入口那个入口节点自己的受管记录，入口切换改 CNAME 目标，节点换 IP 只改节点记录。CNAME 只能有一个值，所以全部发布组和入口节点记录只能用 A；目标取节点受管记录而不是管理员手填的域名，是为了让面板始终能确认 CNAME 最终解析到哪个地址。

## Consequences

- 新建是外部动作，结果未知时（超时）不能盲目重试，否则会建出重复记录：未确认时立即按同名、类型、线路、值读回核对，只认领本次之前不存在的唯一一条匹配记录；否则交给管理员重新绑定，届时那条记录会作为同名候选出现。新建在绑定请求内同步完成，不另存新建意图。
- 改类型接管会覆盖那条记录原来的值和类型，必须由管理员逐条确认；面板仍不删除任何记录。
- 主备组用 CNAME 时，成员只有绑定了已发布的节点记录才能当活动入口；活动入口的节点记录不能解绑或更换，要先切走。
- 记录类型在绑定时定下；主备组首次发布后不能重新绑定（沿用现有限制），要换类型只能新建组。
- ADR 0007 中"面板不新建也不删除记录""全部发布成员绑定管理员预先建好的记录"两处被本 ADR 取代，其余仍然有效。
